# PetHome 总体开发计划与每日执行制度

> 版本：1.0  
> 制定日期：2026-11-15  
> 项目仓库：`shuangrui666/Pethome`  
> 开发投入基线：每天 2 小时、每周 5 天、每周约 10 小时  
> 时间安排：开发时段不固定，以完成当日任务为准  
> 计划周期：第一轮正式可运营版本约 24 周，预留 25–30 周缓冲与试运行  
> 文档性质：长期产品建设路线、阶段验收标准和日常执行规则；不是功能已完成声明。

## 1. 项目最终目标

PetHome（宠物家园）不是一次性课程展示页面，而是准备长期运营的真实宠物服务平台。

**产品定位：综合宠物服务平台 + RAG 智能养宠系统 + AI 多业务应用 + 智能项圈物联网系统。**

平台以宠物数字档案为中心，连接宠物主人/家庭、宠物服务、领养救助、寻宠、社区、知识、AI 和智能设备。

长期业务范围：

1. 用户账户、个人资料、家庭成员和权限。
2. 宠物档案、宠物照片、健康与就诊记录。
3. 领养与救助：发布、审核、申请、沟通和状态管理。
4. 寻宠与发现：走失发布、线索提交、审核、状态更新；地图和距离匹配必须建立在真实定位/地理编码服务上。
5. 宠物服务：医疗、寄养、训练等服务商、服务项目和预约。
6. 社区：帖子、评论、互动、举报和内容治理。
7. 运营后台：用户、内容、服务商、举报、业务状态和审计记录。
8. RAG 养宠知识：可信资料、检索、模型生成、来源引用和质量评估。
9. AI 业务应用：按数据和评估条件逐项上线，不把规则或固定文本伪装成 AI。
10. 智能项圈 IoT：真实设备绑定、通信、位置/活动数据、设备状态和安全控制。

**范围边界：** 商品交易、在线支付、医疗诊断、复杂 AI 模型和智能项圈均属于需要额外服务、资质、资金、数据或硬件验证的扩展项，不因页面存在就视为已上线。宠物健康 AI 只提供有边界的辅助信息，不代替兽医诊断。

## 2. 当前工程原则

- 保留现有 Next.js、Express/TypeScript、MongoDB 技术栈和有价值代码，先审计再修复，不进行无依据的整体重写。
- 根目录 `app/`、`client/`、`server/` 的职责以仓库审计和可复现构建结果为准；未经审计不得删除重复目录。
- 优先模块化单体，先形成稳定业务闭环，不提前拆微服务。
- 先修复安全、数据一致性、核心 API 和测试基础，再扩展新功能。
- 所有功能状态必须区分：规划、页面存在、代码实现、已构建、已集成、已验收、已上线。
- 不提交密钥、真实用户隐私数据或未经脱敏的生产数据。
- 数据删除、模型拆分、索引调整和迁移必须先备份、制定回滚/兼容方案并验证历史数据。
- Git 使用独立工作分支；不得未经明确批准直接改写主分支、强制推送或执行破坏性操作。
- WorkBuddy 是主要代码实施者；实施结果必须由独立测试证据验收，不能以工具自述代替验收。

## 3. 开发时间与每周工作制度

### 3.1 固定投入

| 项目 | 标准 |
|---|---:|
| 每日开发时间 | 2 小时 |
| 每周开发天数 | 5 天 |
| 每周投入 | 约 10 小时 |
| 每周复盘 | 纳入第 5 个开发日 |
| 开发时段 | 不固定，按任务完成情况安排 |

不要求每天固定几点开始。若课程或其他安排冲突，可调整当天时段，但不能把未测试的修改算作完成。某周实际投入不足时，应顺延计划，不压缩必要测试。

### 3.2 每个开发日的 120 分钟

| 用时 | 工作 | 当日输出 |
|---|---|---|
| 10 分钟 | 查看上次记录、Git 状态和遗留问题 | 明确唯一主要目标 |
| 20 分钟 | 阅读相关代码、接口、模型和风险 | 修改方案与验收条件 |
| 60 分钟 | WorkBuddy 实施或定位问题 | 代码/测试/文档变更 |
| 20 分钟 | 运行测试、浏览器验证、数据库验证 | 可复现的结果 |
| 10 分钟 | 检查 diff、提交或记录阻塞 | Git 提交或问题记录 |

复杂问题可以在当天只完成定位，不强迫冒险修改。必须留下根因假设、证据、影响范围和下一步。

### 3.3 每周五天节奏

| 开发日 | 重点 | 交付 |
|---|---|---|
| 第 1 天 | 分析与拆解 | 现状、范围、风险、验收标准 |
| 第 2 天 | 核心实施 | 最小必要代码修改 |
| 第 3 天 | 完成业务逻辑 | API、数据库、权限、异常处理 |
| 第 4 天 | 集成测试 | 正常、失败、越权和边界测试 |
| 第 5 天 | 周验收与提交 | 测试证据、Git 提交、状态更新、下周任务 |

一周只设一个主要目标，可包含必要子任务。遇到阻塞先处理阻塞，不同时开启多个未完成模块。

## 4. 24 周第一轮建设路线

> 这是按每周约 10 小时制定的估算计划，不是不可变的截止日期。每两周根据真实验收情况调整。复杂支付、外部服务审批、真实设备联调等可能延长周期。

| 周次 | 阶段 | 主要工作 | 阶段交付/验收 |
|---|---|---|---|
| 1–3 | P1 工程基础治理 | 收敛当前修改；确认正式前后端入口；修复高优先级 API 契约；身份认证与服务端权限；数据库模型和迁移；构建、测试、日志、环境配置 | 前后端可重复构建；核心 API 有契约；关键权限测试通过；历史数据安全；形成可重复测试方法 |
| 4–6 | P2 用户与宠物档案 | 注册、登录、退出、个人资料；宠物新增/列表/详情/修改/删除；宠物归属权限；健康与就诊记录 | 独立用户可管理自己的宠物；刷新后数据仍存在；用户间数据隔离；错误和越权测试通过 |
| 7–9 | P3 领养与寻宠 | 领养信息发布、审核、搜索、详情、申请与状态；寻宠发布、线索提交、审核和状态更新 | 真实用户可发布；管理员可审核；申请/线索能保存和追踪；没有虚构地理位置或假匹配 |
| 10–11 | P4 服务预约 | 服务商资料、服务项目、可预约信息、预约提交、接受/拒绝/取消、状态通知 | 用户和服务方/管理员可完成预约流程；重复提交、冲突和权限场景有测试 |
| 12–14 | P5 社区与运营后台 | 帖子、评论、互动、举报；用户管理、内容审核、服务管理、操作记录 | 社区数据真实持久化；举报可处理；管理员权限由后端验证；管理操作可追溯 |
| 15–18 | P6 RAG 知识服务 | 资料来源审查与授权；清洗、切分、入库；检索；接入真实模型；来源引用；安全边界和评估集 | 回答基于可追溯资料；展示来源；检索和回答质量有测试；模型不可用时有明确降级 |
| 19–22 | P7 AI 业务应用 | 选定优先业务场景；定义输入/输出、数据授权、基线和评估；逐项实现并集成 | 每个上线 AI 功能都有真实模型/算法、数据来源、评估结果、失败处理和边界说明 |
| 23–24 | P8 正式运营准备 | 安全复核、隐私政策/用户协议、数据备份恢复、日志监控、部署、性能和可用性测试、试运行准备 | 生产环境配置和部署记录；恢复演练；核心流程回归；已知限制和运维手册 |

### 4.1 25–30 周缓冲与试运行

- 修复阶段验收中发现的缺陷，不以新增功能填满时间。
- 邀请小范围真实用户试用，取得明确授权并收集反馈。
- 验证客服/举报/内容审核、数据删除请求、备份恢复和故障处理流程。
- 只有在基础业务稳定后，才逐步增加商城、支付、地图服务和更多 AI 能力。

### 4.2 智能项圈独立工作流

智能项圈与 Web 平台有依赖，但不能虚报为 24 周内必然完成。硬件工作至少要验证：设备型号和传感器能力、供电与续航、设备身份、通信方式、数据签名/认证、设备与宠物绑定、数据上传、断网缓存、异常处理、用户授权和隐私保护。GPS 必须有真实定位硬件和通信链路；温度传感器读数不能直接称为宠物核心体温。任何触觉/刺激功能都必须经过独立硬件安全评估和主人授权，不能由 AI 自主触发。

| 开发日 | 任务 | 验收证据 |

| 第 1 天 | 收敛 Training 与 Enrollment 数据模型拆分 | 检查旧集合历史报名数据；新旧数据读取兼容/迁移方案；重复报名、取消报名、我的报名、课程 CRUD 测试 |

| 第 3 天 | 核对核心 API 契约 | 逐项记录前端路径、方法、请求字段、后端路由、响应结构；修复并测试优先级最高的一批 |

第一周的重点是验证已有工作，不是默认所有任务已经完成。若 Training 历史数据迁移或权限测试不通过，应继续修复，不进入依赖它们的新功能开发。

## 6. 功能完成的统一验收标准

任何核心业务模块必须按适用项通过以下检查，不能因为页面可打开或接口返回 200 就标记完成：

1. **前端：** 页面真实调用正式 API；加载、空状态、错误状态和提交结果明确；没有把 mock 数据当成真实数据。
2. **后端：** 路由、控制器、验证、错误处理和响应结构正确；未授权请求被拒绝。
3. **数据库：** 数据真实写入并可读取；字段、关联、索引和迁移有说明；刷新/重新登录后仍存在。
4. **权限：** 测试未登录用户、普通用户、资源所有者、非所有者和管理员等适用身份；关键权限由服务端实施。
5. **业务流程：** 正常路径、重复提交、无效输入、取消/删除、异常和边界场景有测试。
6. **质量：** 类型检查、构建、相关自动化测试通过；检查日志、密钥、个人信息和无关 diff。
7. **证据：** 保存测试命令、结果、必要的脱敏截图/响应、数据库验证说明和 Git 提交 SHA。
8. **状态：** 只有所有适用验收条件通过，才标记“已通过”；部署还必须有真实线上访问和生产环境验证证据。

### 6.1 状态定义

| 状态 | 定义 |
|---|---|
| 未开始 | 尚未实施 |
| 进行中 | 正在分析或修改 |
| 待验收 | 代码已修改，但证据尚不完整 |
| 已通过 | 所有适用验收标准均有证据 |
| 阻塞 | 存在明确依赖或问题，暂时无法推进 |

“已提交”不等于“已通过”；“构建成功”不等于“业务闭环”；“已部署”不等于“可以安全运营”。

## 8. 每周验收和调整规则

每周第 5 个开发日完成：

1. 对照本周任务逐项验收，不以代码行数、修改文件数或 AI 工作时长作为成果。
2. 统计计划任务数、通过数、待验收数、阻塞数和未解决高优先级问题。
3. 复查本周 Git 提交、分支和变更范围。
4. 更新本文件关联的项目状态文档和实际证据链接。
5. 选择下周一个主要目标；未通过的前置任务优先继续处理。
6. 每两周评估一次剩余工作量和 24–30 周估算，不通过降低测试标准来追赶日期。

## 9. 优先级规则

优先顺序：

1. P0：安全漏洞、数据丢失、越权访问、密钥泄露、构建阻塞。
2. P1：核心用户流程不可用、API 契约不匹配、数据库错误、数据一致性问题。
3. P2：测试覆盖、日志监控、可维护性和部署可靠性。
4. P3：视觉细节、非核心体验优化和新增功能。

同一时间只允许一个主要工程目标。不得在核心流程尚未验收时，不断切换到首页美化、AI 新点子或硬件新功能。
