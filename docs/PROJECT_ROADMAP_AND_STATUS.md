# PetHome 项目推进路线与状态总表

> **文档用途：** 本文件是 PetHome 项目整体推进顺序、阶段状态、证据和下一步工作的统一管理入口。  
> **维护原则：** 以仓库代码、可复现的测试结果和实际运行证据为准；规划文档不等于功能实现，代码存在不等于功能可用。  
> **当前基线日期：** 2026-11-13  
> **当前主线：** 第一阶段——工程审计与项目定型。

---

## 1. 项目目标与范围

PetHome 计划逐步建设为综合宠物服务平台，并在基础平台稳定后探索智能项圈、物联网数据接入和 AI 辅助能力。

长期目标包括：

- 宠物服务网站：宠物档案、领养、医疗服务、救助、走失寻回、托管、用品、训练和社区交流等。
- 智能项圈与物联网：设备绑定、定位与活动数据接入、历史记录、电子围栏、通知、多宠物与家庭共享、社区协同寻宠，以及经过安全评估的舒适护理能力。
- AI 辅助：在具备合规数据、明确任务和评估证据后，逐步探索行为分析、个体趋势、异常变化提示和走失线索辅助匹配。
- 工程基础：清晰的前后端边界、数据库与 API、身份认证和权限、安全、自动化测试、持续集成、部署和可维护文档。

以上是项目目标范围，不代表这些功能当前均已实现或上线。

## 4. 第一阶段执行清单

按顺序推进；每一步完成后记录证据、问题和结论，再进入下一步。

### 4.1 仓库结构盘点

- [ ] 获取主分支完整目录树。
- [ ] 标记前端、后端、共享代码、配置、测试、文档、静态资源和脚本目录。
- [ ] 识别重复目录、历史遗留目录、生成文件和疑似未使用文件。
- [ ] 对不确定的目录先标记“待确认”，不直接删除。

**产出：** 仓库结构清单和目录职责说明。

### 4.2 正式前端入口确认

- [ ] 检查根目录及 `client/` 等候选目录。
- [ ] 对比 `package.json`、锁文件、Next.js 配置、页面目录和构建脚本。
- [ ] 核实 Netlify 等部署配置实际指向哪个目录和构建产物。
- [ ] 明确唯一正式前端入口；如存在多个应用，说明各自用途和关系。

**产出：** 前端入口结论及对应文件证据。

### 4.3 后端与数据库核查

- [ ] 确认后端启动入口和实际运行脚本。
- [ ] 梳理路由、控制器、服务层、中间件和数据模型。
- [ ] 核对数据库类型、连接方式、模型定义和迁移/初始化方式。
- [ ] 检查认证、授权、输入校验、错误处理和日志。
- [ ] 检查前端 API 调用与后端路由是否对应。

**产出：** 实际技术架构和 API 对照清单。

### 4.4 功能实现状态核查

每项功能使用以下状态之一：

- **已验证：** 代码链路存在，且有可复现测试或运行证据。
- **代码已实现、待验证：** 找到实现代码，但尚无充分运行或测试证据。
- **部分实现：** 只有部分流程或边界条件完成。
- **模拟/占位：** 使用 mock、静态数据、假接口或 TODO。
- **仅规划：** 只出现在 README、架构图或规划文档中。
- **未发现：** 在已检查范围内没有找到实现证据。
- **待确认：** 证据不足，暂时不能判断。

**产出：** 功能—页面—API—数据模型—测试证据对照表。

### 4.5 本地构建、启动与测试

- [ ] 先确认项目要求的运行环境和依赖版本。
- [ ] 按项目说明安装依赖，不擅自覆盖用户环境或删除文件。
- [ ] 执行现有 lint、类型检查、构建和测试脚本。
- [ ] 按实际入口尝试启动前端和后端。
- [ ] 记录命令、执行环境、成功/失败结果和完整错误摘要。
- [ ] 对未能运行的项目明确记录阻塞原因，不把静态检查当作运行成功。

**产出：** 可复现的本地验证记录。

### 4.6 工程审计报告

- [ ] 汇总已核实的技术架构。
- [ ] 汇总功能实现状态和证据。
- [ ] 按严重程度、影响范围和修复成本排列问题。
- [ ] 给出每个高优先级问题的修复建议和验收方法。
- [ ] 根据审计结论更新第二阶段的实际开发顺序。

**产出：** 工程审计报告和下一阶段任务清单。

## 5. 统一工作规则

### 5.1 证据优先

任何“已完成”“可用”“已上线”的结论都必须附有可核验依据，例如文件路径、代码调用链、测试名称与结果、构建日志或部署记录。

### 5.2 严格区分四种进度

| 层次 | 示例 | 能证明什么 |
|---|---|---|
| 规划 | 架构图中设计了电子围栏 | 需求或架构方向已记录 |
| 文档 | 开发手册写明电子围栏规则 | 设计方案已记录 |
| 代码 | 后端存在越界判断接口 | 有相关代码，仍需验证 |
| 验收 | 真实定位数据触发规则并成功通知，且测试通过 | 对应端到端场景已验证 |

### 5.3 每个任务的固定流程

1. 说明任务属于哪个阶段，以及现在做它的原因。
2. 明确要检查或修改的文件、预期结果和完成标准。
3. 优先读取现有内容和证据，不盲目重写。
4. 修改前确认影响范围；涉及重要文件时先备份或保留可恢复版本。
5. 修改后重新读取文件，并执行适用的检查或测试。
6. 记录结果、证据、未解决问题和下一步。
7. 更新本文件的状态表，避免聊天记录成为唯一进度来源。

### 5.4 防止任务偏移

- 与当前阶段无关、且不会解除当前阻塞的问题，先放入待办，不自动切换主线。
- 新增架构图、规划文档或学习资料，不能替代代码审计、运行验证和测试。
- 不因发现一个局部问题就无限扩展范围；先判断严重程度和对当前主线的影响。
- 不在没有审计结论前大规模重构、删除目录或新增复杂功能。

### 5.5 安全与真实性边界

- 家庭共享、社区寻宠和设备数据访问必须由服务端实施身份与权限校验，不能只依靠前端隐藏按钮。
- 电子围栏属于规则与定位数据处理能力，不应被描述为 AI 模型能力。
- GPS/GNSS 设备不会自动把位置传到网站，必须验证真实通信和后端接入链路。
- 项圈温度数据不能直接等同于宠物核心体温。
- 舒适护理/触觉反馈不得由 AI 自主触发；必须先完成硬件安全评估、主人授权、强度和时长限制、本地保护与停止机制。
- AI 能力必须有真实数据来源、标签、基线、测试集和评估结果；规则匹配或模拟数据不等于训练好的机器学习模型。

这些事项在对应阶段开始时重新评估，不代表永久取消。
