## 1. 产品定位与总体目标

### 1.1 正式产品定位

**PetHome（宠物家园）定位为：综合宠物服务平台 + RAG 智能养宠系统 + AI 多业务应用 + 智能项圈物联网系统。**

四个组成部分共同构成一个平台，而不是四个独立网站：

1. **综合宠物服务平台：** 提供宠物档案、健康记录、领养救助、走失寻回、医疗、托管、训练、用品、社区和预约等基础服务。
2. **RAG 智能养宠系统：** 以可信宠物知识库为基础，通过检索增强生成（RAG）和大语言模型，为用户提供可追溯、有来源、有边界的养宠知识服务。
3. **AI 多业务应用：** 将图像识别、推荐、风险辅助分析、行为分析和资源匹配等 AI 能力嵌入具体业务，而不是只提供一个孤立的聊天机器人。
4. **智能项圈物联网系统：** 接入真实设备数据，为宠物档案提供位置、活动、设备状态和传感器趋势，并为后续 AI 分析提供数据基础。

### 1.2 核心产品关系

平台以**宠物数字档案**为中心，连接主人/家庭、服务、知识、设备、数据和社区。

```
                  PetHome 2.0
                      |
              宠物数字档案中心
                      |
       +--------------+--------------+
       |              |              |
   宠物服务        智能养宠         智能设备
       |              |              |
  领养/医疗       RAG知识库        项圈/传感器
  救助/寻回       LLM问答          位置/活动
  社区/预约       AI业务应用       设备事件
       |              |              |
       +--------------+--------------+
                      |
             统一用户、权限、数据、
             API、通知与安全体系
```

例如：用户创建宠物档案并记录健康情况；在智能养宠中咨询时，系统在用户授权后读取相关档案并检索知识库；项圈接入后，活动数据进入同一宠物档案；经验证的 AI 模型再利用这些数据提供趋势提示。各模块共享身份和数据关系，但必须按权限隔离。

### 1.3 本次重构要解决的问题

- 旧网站页面风格、导航和信息架构需要统一，不能只在旧首页上局部打补丁。
- 根目录前端与 `client/` 高度重复，需要确定唯一正式前端入口。
- 前后端 API 路径、HTTP 方法、字段和响应结构存在静态审计发现的错配。
- 部分页面存在 mock/静态数据或缺少真实数据来源的统计。
- 认证、宠物档案、领养、寻回、医疗、社区和服务等流程需要形成真正闭环。
- RAG、AI 和物联网必须建立在真实数据、明确权限、评估机制和安全边界上。
- 需要区分规划、设计、代码、测试和上线状态，不把概念页面当作真实功能。

### 1.4 总体原则

- 保留有价值的现有代码，先审计再决定复用、修复或重写。
- 以宠物数字档案为统一业务实体，避免各模块重复维护互不关联的数据。
- 先保证基础平台和核心业务，再建设 RAG，再逐步扩展 AI 模型和项圈接入。
- 规则引擎、RAG、传统机器学习、视觉模型和大语言模型要明确区分。
- 所有 AI 输出均需说明依据和不确定性；医疗内容不替代兽医诊断。
- 家庭共享、健康信息、位置、设备和 AI 个性化数据必须经过后端授权。
- 每个阶段可构建、可测试、可回退；功能完成必须有证据。

## 2. 用户角色与核心场景

| 用户角色 | 主要目标 | 权限边界 |
|---|---|---|
| 访客 | 浏览平台介绍、公开领养信息、服务和社区内容 | 仅访问公开内容 |
| 宠物主人 | 管理宠物、健康、服务、知识助手和设备 | 管理本人拥有或获授权的宠物 |
| 家庭成员 | 共同照护宠物 | 按主人授予的宠物范围和角色操作 |
| 领养申请人 | 浏览宠物、提交申请、跟踪进度 | 仅查看本人申请及公开信息 |
| 救助人员/机构 | 发布救助信息、处理线索、协助领养 | 按机构身份和授权范围访问 |
| 服务商家/机构 | 管理资料、服务和预约 | 仅管理所属机构数据 |
| 管理员/审核员 | 审核内容、处理举报、平台运营 | 独立后台权限，关键操作留审计记录 |

核心用户旅程：

1. **建立档案：** 注册/登录 → 创建宠物 → 填写资料 → 添加健康记录 → 按需邀请家庭成员。
2. **日常养宠：** 选择宠物 → 使用 RAG 助手 → 查看来源依据 → 保存有用建议或建立照护提醒。
3. **使用服务：** 选择宠物 → 查找医院/托管/训练等服务 → 查看详情 → 预约/申请 → 跟踪处理状态。
4. **走失寻回：** 选择宠物 → 发布走失事件 → 社区提交目击线索 → AI 可辅助排序 → 主人/救助人员人工核实。
5. **设备接入：** 绑定项圈 → 设备身份验证 → 接收数据 → 查看位置/活动/设备状态 → 设置电子围栏。
6. **AI 辅助：** 取得合规数据 → 质量检查和标注 → 检索或模型推理 → 展示依据与不确定性 → 用户反馈。

| 智能项圈/IoT | 智能设备 | **新增** | 设备身份、通信、数据协议、接入 API、存储和规则引擎 |

### 4.1 代码处置规则

- **保留：** 已有实现与新业务边界一致，且安全、测试和接口验证通过。
- **修复：** 业务方向正确，但存在字段、接口、权限、异常处理或数据问题。
- **重做：** 页面/流程与新产品体验冲突，或原实现缺少可靠数据链路。
- **新增：** 当前没有实现证据的 RAG、AI、设备等能力。
- **暂缓/移除：** 无真实数据、无明确业务价值或有安全风险的占位功能。删除前必须检查引用和保留回退方案。

## 5. RAG 智能养宠系统设计（核心创新主线）

### 5.1 产品目标

RAG 不是一个普通聊天框，而是 PetHome 的知识服务底座。它应基于经过筛选的宠物知识资料检索相关内容，再由大语言模型组织回答，尽可能提供可追溯来源，并明确知识不足和专业边界。

首批服务范围：

- 日常养宠知识、喂养、清洁和环境管理。
- 疫苗、驱虫和常规护理知识。
- 常见症状相关科普、就医准备和风险提示。
- 宠物药品说明和用药知识检索。
- 基于授权宠物档案的个性化养护建议。
- 养护计划、日程和记录整理。

### 5.2 建议的 RAG 流程

```
可信知识来源
  ├─ 经审核的宠物护理资料
  ├─ 可靠的疾病/症状科普资料
  ├─ 药品说明与权威公开资料
  └─ PetHome 自有审核知识
          |
          v
知识处理流水线
  ├─ 来源登记与授权检查
  ├─ 文档解析、清洗、去重
  ├─ 分段与元数据标注
  ├─ 版本管理与审核状态
  └─ 向量化与索引
          |
          v
用户问题与权限检查
          |
          v
检索/重排/相关性判断
          |
          v
组合检索证据 +（经授权的）宠物档案上下文
          |
          v
LLM 生成受约束回答
          |
          v
来源引用、风险提示、不确定性、用户反馈
```

### 5.3 必须具备的系统模块

| 模块 | 职责 |
|---|---|
| 知识来源管理 | 记录来源、作者/机构、许可、更新时间和审核人 |
| 文档处理 | 解析 PDF/网页/文本，清洗、去重、分段 |
| 元数据体系 | 物种、年龄阶段、主题、适用条件、来源等级、版本 |
| 向量检索 | 根据问题检索相关知识片段 |
| 关键词/混合检索 | 补充专有名词、药品名和精确术语检索 |
| 重排与证据过滤 | 降低无关内容，判断是否有足够证据回答 |
| LLM 编排 | 将问题、证据和经授权的档案上下文组织为回答 |
| 引用与反馈 | 展示来源，收集有帮助/无帮助反馈和错误报告 |
| 知识运营后台 | 审核、更新、下架和追踪知识版本 |

### 5.4 个性化与隐私

宠物档案可包含品种、年龄、体重、性别、过敏、健康记录和既往就诊信息。只有用户明确授权并且当前问题确实需要时，RAG 才能读取相关字段。回答和日志应遵循数据最小化原则，不把敏感档案无必要地发送给模型或记录到普通日志。

### 5.5 安全边界

- 展示检索来源和知识更新时间；无法找到可靠证据时应明确说不知道或建议咨询专业人士。
- 不替代兽医诊断，不自动开药，不生成危险剂量或未经核验的治疗方案。
- 症状相关回答应区分一般科普、紧急风险提示和就医建议。
- 药物知识用于资料解释和核对，不代替兽医处方。
- 知识库内容必须审核来源、版权/使用许可和更新时间。
- 防范提示注入和恶意文档：检索内容只能作为资料，不能覆盖系统安全规则。
- 对高风险问题设置拒答/升级就医策略，并保留必要的安全测试用例。

### 5.6 RAG 验收指标

至少建立测试问题集，并评估：

- 检索召回：相关资料是否被找到。
- 引用准确性：引用是否真正支持回答。
- 忠实性：回答是否超出检索证据。
- 无答案处理：知识不足时是否明确承认。
- 安全性：医疗、药物和紧急问题是否遵守边界。
- 延迟和成本：检索、生成的响应时间和资源消耗。
- 用户反馈：有帮助率、纠错率和问题类别。

初期可以使用规则与人工审核辅助运营，但不能把简单关键词匹配称为成熟 RAG。

## 6. AI 多业务应用体系

AI 应嵌入业务场景，按数据成熟度逐个上线。八个重点方向如下：

| AI 创新方向 | 所属业务 | 输入数据 | 目标能力 | 前置条件/边界 |
|---|---|---|---|---|
| 1. 走失宠物图像匹配 | 走失寻回 | 宠物照片、走失资料、目击照片和时间地点 | 视觉特征提取、相似候选排序 | 需要授权图片、标注和离线评估；只给候选，不自动判定找回 |
| 2. 智能领养匹配 | 领养救助 | 领养人生活方式、经验、居住环境和宠物特征 | 推荐适配候选并解释原因 | 用户自愿填写；避免歧视性推断；最终由人审核 |
| 3. 健康风险辅助提示 | 健康管理 | 症状描述、健康档案、活动趋势和历史记录 | 提醒风险、整理就医信息 | 不做诊断，不替代兽医；高风险情况优先建议就医 |
| 4. 行为分析与训练 | 活动/训练 | 活动传感器、视频或主人记录 | 行为分类、趋势分析、训练建议 | 需定义标签、采集条件和个体基线；不能把相关性当因果 |
| 5. 流浪动物救助调度 | 救助协作 | 地点、救助需求、人员能力、可用资源 | 资源匹配和任务排序 | 规则与优化算法可先行；位置和人员信息需授权 |
| 6. 宠物社交匹配 | 社区 | 宠物体型、性格、活动习惯和主人设置 | 推荐合适的互动对象 | 需用户主动选择公开范围；推荐不保证行为安全 |
| 7. 智能养护管理 | 我的宠物 | 宠物档案、日程、健康记录和主人偏好 | 个性化提醒、计划和记录摘要 | 第一版可先做透明规则提醒，再逐步引入模型 |
| 8. 药物知识助手 | RAG/健康知识 | 药品说明、权威知识和用户问题 | 检索解释药品资料、提示核对事项 | 不开处方、不擅自推荐剂量；遵循兽医指导 |

其他可扩展应用：

- 医院就诊助手：整理症状、就诊问题和病史摘要，辅助查找服务。
- 社区智能服务：内容分类、搜索、问答摘要和违规内容辅助识别。
- 防走失辅助：根据用户授权的位置/设备状态和规则产生提醒。
- 宠物托管/幼儿园：根据照护记录生成活动摘要和个性化照护提示。
- 宠物用品推荐：根据宠物档案和用户明确偏好提供推荐，并标注推荐依据。
- 捐赠/救助匹配：按公开需求、地区和资源约束匹配项目。

### 6.1 AI 能力分层

- **RAG/LLM：** 知识问答、资料解释、记录摘要、就医准备。
- **计算机视觉：** 走失宠物图像相似检索，后续可扩展图像辅助识别。
- **推荐系统：** 领养、用品、服务和宠物社交推荐。
- **机器学习/时序分析：** 活动模式、行为类别和个体趋势变化。
- **规则引擎/优化：** 电子围栏、提醒、救助任务约束匹配。

不得把普通规则判断包装成 AI 模型。每个模型需有任务定义、数据来源、标注规范、基线、训练/测试隔离、指标、错误分析和版本记录。

### 6.2 AI 研发与上线流程

`需求定义 → 数据授权 → 数据质量检查 → 标注 → 数据集版本 → 基线 → 训练/检索配置 → 独立评估 → 安全评估 → 灰度上线 → 监控与反馈`

在真实数据、标注和评估尚未具备时，只能做产品原型或明确标注的演示，不宣称具备准确识别能力。

## 7. 智能项圈与物联网系统

### 7.1 产品功能范围

| 子系统 | 目标功能 | 说明 |
|---|---|---|
| 设备管理 | 绑定、解绑、设备身份、电量、在线状态 | 设备必须有唯一身份和安全配对流程 |
| 定位 | GPS/GNSS 位置、最后可信位置、历史轨迹 | 显示定位时间、精度和数据延迟 |
| 电子围栏 | 安全区域、越界事件和通知 | 属于定位数据与规则引擎，不是 AI |
| 活动监测 | 活动量、静止/运动趋势 | 明确采样率、数据缺失和个体差异 |
| 温度趋势 | 传感器温度曲线 | 传感器读数不等同于宠物核心体温 |
| AI 洞察 | 活动变化、行为辅助分析 | 需要真实数据和独立评估 |
| 家庭共享 | 授权家庭成员查看指定宠物数据 | 后端强制校验授权范围 |

### 7.2 数据链路

`传感器 → 项圈主控 → 无线通信/手机网关 → 设备接入 API → 身份与数据校验 → 数据库 → 规则/分析服务 → PetHome 页面与通知`

GPS 只负责定位，不会自动将位置发送到网站。必须验证通信模块、手机网关或其他真实网络链路。每条数据至少记录设备 ID、宠物关联、数据类型、时间戳、单位、采样/质量信息和接收时间。

### 7.3 设备安全要求

- 设备身份认证、绑定授权和解绑流程。
- 数据传输保护、重放/伪造数据防护和密钥管理。
- 断网、延迟、低电量、异常定位和数据缺失状态提示。
- 位置数据访问范围、保留期限和用户删除/撤销机制。
- 电子围栏采用连续点确认、边界抖动处理和通知冷却，降低误报。
- 设备控制命令需要权限、回执、超时和审计。

### 7.4 舒适护理/触觉反馈安全边界

如果未来设备包含按摩或触觉反馈功能：

- 必须由主人主动操作并明确授权。
- AI 不得自主触发按摩或触觉输出。
- 设备端独立执行强度、持续时间、温度等限制。
- 必须有物理或本地停止机制，超时自动停止，异常立即停止。
- 在完成硬件安全评估和真实测试前，不开放真实控制。
