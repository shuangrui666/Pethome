## 1. 重构目标与基本决策

### 1.1 产品定位

**PetHome（宠物家园）定位为综合宠物服务与智能宠物管理平台。**

平台以宠物档案为核心，把宠物日常管理、健康记录、领养救助、走失寻回、线下服务、社区协作连接起来；在基础平台稳定后，再接入智能项圈、物联网数据和经过真实数据训练评估的 AI 辅助能力。

PetHome 不应只是宠物资讯展示页或功能入口集合，而应形成“宠物—主人/家庭—服务—设备—数据—社区”的连续业务体验。

### 1.2 本次重构要解决的问题

1. 现有页面视觉和信息架构需要统一，不能继续只在旧首页上局部打补丁。
2. 现有仓库存在根目录前端与 `client/` 高度重复的情况，必须确定唯一正式前端入口。
3. 前后端 API 路径、HTTP 方法、字段和响应结构存在静态审计发现的错配。
4. 部分页面使用 mock/静态数据或虚构统计，必须明确区分演示数据与真实业务数据。
5. 核心用户流程需要闭环：注册登录、宠物档案、领养/寻回、服务预约、社区互动等。
6. 智能项圈与 AI 创新功能需要有真实设备、数据、权限、算法评估和安全机制作为基础。

### 1.3 重构原则

- **保留价值，不盲目推倒。** 优先复用已有认证、数据模型、控制器和业务代码；经审计确认不适合复用的部分再重写。
- **先统一产品，再重构页面。** 先确定导航、页面清单、用户流程和 API 契约，再逐页实现。
- **先打通核心业务，再扩展创新能力。** 不以页面数量或视觉效果代替功能完成度。
- **真实数据优先。** 不用 mock 数据冒充真实用户、医院、商家、统计或设备数据。
- **后端强制权限。** 家庭共享、宠物数据、设备控制和社区隐私范围必须在服务端校验，不能只依赖前端隐藏按钮。
- **每个阶段都可验证、可回退。** 变更前记录基线，变更后执行构建、测试和验收。
- **规划、文档、代码、测试、上线分别记录。** 不能把“已规划”写成“已实现”，也不能把“代码存在”写成“验收通过”。

## 2. 产品用户与核心场景

### 2.1 用户角色

| 用户角色 | 主要目标 | 主要权限边界 |
|---|---|---|
| 访客 | 浏览平台介绍、领养信息、服务和公开社区内容 | 只能访问公开内容 |
| 宠物主人 | 管理宠物、记录健康、使用服务、管理设备 | 只能管理本人拥有或获授权的宠物 |
| 家庭成员 | 与主人共同照护宠物 | 按主人授予的宠物范围和角色操作 |
| 领养申请人 | 浏览宠物、提交申请、查看申请进度 | 只能查看本人申请及公开信息 |
| 救助人员/机构 | 发布救助信息、处理走失线索、协助领养 | 按机构身份和授权范围访问 |
| 服务商家/机构 | 管理服务资料、预约和订单 | 只能管理所属机构的数据 |
| 平台管理员/审核员 | 内容审核、举报处理、平台运营 | 使用独立后台权限，操作留审计记录 |

角色和权限需要在后端定义；具体角色是否开放注册、是否需要人工审核，进入实现阶段再确定。

### 2.2 核心用户旅程

1. **新用户建立宠物档案：** 注册/登录 → 创建宠物 → 填写基础资料 → 添加健康记录 → 按需邀请家庭成员。
2. **主人使用服务：** 选择宠物 → 查找医院/托管/训练等服务 → 查看服务详情 → 预约或提交申请 → 查看处理状态。
3. **走失寻回：** 选择宠物 → 发布走失事件 → 查看最后可信位置 → 社区用户提交线索 → 主人/救助人员人工核实 → 更新事件状态。
4. **智能项圈接入：** 绑定设备 → 设备身份校验 → 设备数据接入 → 展示位置/活动/设备状态 → 设置电子围栏 → 接收规则事件提醒。
5. **AI 辅助分析：** 取得有质量的数据 → 建立人工标注 → 训练与独立评估 → 输出带依据和不确定性的辅助结果 → 用户确认或反馈。

## 4. 核心功能如何连接

### 4.1 以宠物档案作为业务中心

宠物档案是多个模块共同引用的核心实体。领养、健康、服务预约、设备、活动趋势和家庭共享都应关联到明确的宠物 ID。

基本关系：

`用户/家庭成员 → 授权关系 → 宠物档案 → 健康记录/预约/设备/活动/走失事件`

任何业务数据都要确认所属用户、宠物和访问权限，不能仅凭前端传入的 ID 判定用户有权操作。

### 4.2 账户与家庭共享流程

1. 用户注册并登录。
2. 创建或认领宠物档案。
3. 主人发起家庭邀请。
4. 被邀请人接受邀请。
5. 后端建立家庭成员、角色、宠物范围和权限记录。
6. 每次读取或修改宠物资料时，后端重新校验授权。
7. 主人可撤销邀请或成员权限；撤销后后端立即拒绝后续未授权访问。

### 4.3 智能项圈数据流程

`传感器 → 项圈主控 → 无线通信/手机网关 → 设备接入 API → 身份与数据校验 → 数据存储 → 规则服务/分析服务 → 网页展示与通知`

关键要求：

- GPS/GNSS 只负责定位，不会自动将数据传给网站；必须有真实通信链路。
- 设备必须有唯一身份，绑定和解绑要有授权流程。
- 每条数据应带设备标识、宠物关联、时间戳、数据类型和质量信息。
- 断网、低电量、定位不可信、数据延迟时，界面必须如实显示状态。
- 位置历史和家庭共享要有权限边界、保留策略和用户控制。

### 4.4 电子围栏流程

电子围栏是**定位数据处理与规则引擎**，不是 AI：

1. 主人设置安全区域和通知规则。
2. 后端验证设备、宠物和用户权限。
3. 接收位置数据并判断定位质量、时间戳和有效性。
4. 规则服务判断是否越界，并处理边界抖动、连续点确认和冷却时间。
5. 生成事件并向有权限的家庭成员发送通知。
6. 记录规则版本、触发数据和通知结果，供用户查看。

定位数据质量不足时，不应把不确定位置包装成确定的越界事件。

### 4.5 走失寻回与社区协作流程

`宠物档案 → 发布走失事件 → 最后可信位置/时间 → 公开范围控制 → 社区目击线索 → 后端权限与内容校验 → 主人/救助人员人工核实 → 更新状态`

AI 可以在数据和评估充分后辅助图片或线索排序，但不能自动认定某只宠物已经找到。位置公开范围、联系方式和个人信息必须由用户控制并受服务端规则保护。

### 4.6 AI 数据与模型流程

`数据采集 → 质量检查 → 人工标注 → 数据集版本 → 训练/验证/测试 → 指标评估 → 模型版本 → 服务部署 → 用户反馈与监测`

第一批候选方向：

- 宠物活动/行为分类辅助识别。
- 基于个体历史基线的活动趋势变化提示。
- 走失宠物图片和目击线索辅助匹配。

每个模型必须有明确任务定义、标签说明、训练/测试划分、基线模型、评估指标和错误分析。规则判断不能冒充机器学习模型；没有真实数据和评估结果时，只能标记为规划或实验功能。

AI 结果是辅助信息，不构成兽医诊断。结果应展示数据时间范围、依据和不确定性，并提供人工确认入口。

### 4.7 舒适护理/触觉反馈安全流程

舒适护理不是 AI 自动执行功能。若未来硬件包含触觉反馈模块，必须满足：

- 主人主动操作并明确授权；
- 后端校验账户、宠物、设备绑定关系；
- 设备端独立执行强度、持续时间和温度等安全限制；
- 有物理或本地停止机制；
- 超时自动停止，异常立即停止；
- 记录指令、设备确认和停止状态；
- AI 不得自主触发按摩或触觉反馈。

在硬件安全评估和真实测试完成前，不开放真实控制，只能展示设计说明或模拟界面，并明确标记为演示。

## 5. 技术架构与工程组织

### 5.1 当前工程基线

目前本地已确认的工作目录是 `E:\\Pethome-GitHub`。已知结构包括：

- 根目录 `app/`：Next.js 页面入口候选，也是当前本地启动的前端目录。
- 根目录 `components/`：共享组件。
- 根目录 `src/`：前端 API 与工具代码。
- `server/`：Express/TypeScript 后端独立工程。
- `public/`：静态资源。
- `docs/`：项目文档。
- `client/`：存在与根目录高度重复的另一份前端目录，最终用途尚未确定。

**本次不立即把目录改名为 frontend/backend，也不立即移动或删除 `client/`。** 先完成正式入口、构建配置、部署配置和重复文件审计，再决定是否需要目录迁移。避免因为重排目录破坏导入路径、构建、部署或 Git 历史。

### 5.2 目标逻辑架构

| 层次 | 主要职责 | 实施原则 |
|---|---|---|
| Web 前端 | 页面、交互、表单、数据展示 | 统一设计系统；页面只调用明确的 API 契约 |
| API 后端 | 认证、业务规则、权限、数据访问 | 统一路由、校验、错误格式和日志规范 |
| 数据库 | 用户、宠物、家庭、业务记录、设备和事件 | 明确关联、索引、数据保留和迁移策略 |
| 文件存储 | 宠物照片、帖子图片、证明材料 | 不把大文件随意存进业务文档；校验类型和权限 |
| 实时通信 | 通知、设备状态、消息 | 仅在认证、房间授权和断线处理验证后启用 |
| 设备接入 | 设备身份、数据上报、命令回执 | 独立的设备协议和数据校验边界 |
| AI 服务 | 数据处理、模型推理、评估和版本管理 | 与普通业务 API 分离；输出可追踪、可评估 |

### 5.3 API 契约治理

建立统一 API 契约清单，至少包含：

- 模块、方法、路径、认证要求、角色/资源权限；
- 请求参数、字段类型、必填规则；
- 响应结构、分页格式、错误码；
- 对应前端调用文件、后端路由、控制器和数据模型；
- 自动化测试用例和当前验证状态。

建议以 OpenAPI 文档作为接口契约来源。新增或修改接口时，前后端必须同步更新并执行契约测试。禁止前端调用未登记的路径，禁止通过 mock fallback 掩盖接口失败。

### 5.4 统一前端设计系统

重做页面前先建立：

- 色彩、字体、间距、圆角、阴影和响应式断点；
- 按钮、输入框、卡片、标签、弹窗、表格、空状态、错误状态；
- 导航栏、页脚、面包屑和页面容器；
- 加载、无数据、权限不足、网络失败和重试状态；
- 图片比例、裁切、占位图、加载失败回退规则。

视觉方向建议：温暖、可信、现代、清晰；避免过度卡通化或把每个页面做成不同模板。图片必须来自仓库中真实存在且授权可用的资源，或来自经过审核的图片服务；不能依赖无法验证的临时外链。

## 9. 质量、真实性与安全验收标准

每个模块交付时至少检查：

1. **页面：** 路由可访问、导航有效、桌面/移动端布局正常。
2. **数据：** 数据来源真实可追溯；空数据、加载失败和权限不足有明确状态。
3. **接口：** 请求路径、方法、字段、响应和错误码与契约一致。
4. **权限：** 未登录、无资源权限、跨用户访问和家庭成员权限均有测试。
5. **安全：** 不记录密码/token；上传文件服务端校验；敏感信息最小化展示。
6. **可靠性：** 网络中断、接口超时、重复提交、并发修改和数据缺失有处理。
7. **可维护性：** 代码有明确职责、必要测试、文档和变更记录。
8. **真实性：** 不把占位内容、模拟数据、规划图或静态页面标为真实已上线能力。

建议状态统一使用：

- `规划中`
- `设计完成`
- `开发中`
- `代码完成，待验证`
- `测试通过`
- `已部署，待观察`
- `已验收`
- `阻塞`

只有达到对应证据要求才允许升级状态。
