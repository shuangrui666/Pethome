### 2.1 系统边界与责任划分

PetHome 的目标系统可按以下逻辑层次设计。层次是架构边界，不代表当前仓库已经具备全部服务：

1. **设备层：** 智能项圈、MCU、GPS/GNSS（如硬件配置支持）、IMU、温度或其他实际安装的传感器、震动/触觉输出模块及电源管理。
2. **通信层：** 设备身份认证、数据加密传输、网络连接状态、重试与缓存策略。具体协议和通信方式待硬件与网络条件评估后确定，不预设 MQTT、HTTP 或其他协议已经落地。
3. **后端接入层：** 接收设备上报，验证设备身份、数据格式、时间戳和数据归属，执行限流、去重、错误处理和审计。
4. **存储层：** 按宠物、设备和时间组织定位、传感器、设备状态、围栏事件、护理指令及操作记录；具体数据库、时序存储和保留周期待审计与设计。
5. **业务规则与 AI 层：** 负责位置可信度判断、电子围栏规则、家庭权限、走失事件协作和 AI 分析。规则引擎与 AI 模型应保持清晰边界。
6. **应用层：** 网站或移动端展示宠物档案、设备状态、位置、活动趋势、告警、家庭共享和经授权的设备控制入口。

### 2.2 关键业务边界

- **电子围栏是规则功能：** 由主人设置区域，系统结合定位数据、数据新鲜度和可信度执行规则判断；不能将其描述为 AI 自动识别。
- **家庭共享是身份与权限功能：** 必须由后端进行资源级授权，不能仅靠前端隐藏按钮。
- **社区协同寻宠是授权和人工核验流程：** 需管理走失事件、最后可信位置、线索提交、信息可见范围、主人授权和人工核验。
- **AI 是辅助分析能力：** 行为识别、趋势分析、异常变化提示和线索匹配都需要合规数据、算法/模型、测试和效果评估。
- **舒适护理是受安全约束的设备控制功能：** 必须由主人明确授权启动，不能由 AI 分析结果自动触发。

## 5. 系统架构与智能项圈数据流

### 5.1 端到端数据流（规划）

规划中的数据上行链路：

1. 项圈传感器采集数据，并由 MCU 生成设备标识、关联标识、采集时间和数据类型等必要元信息。
2. 设备按确定的通信方案发送数据；网络不可用时，应按设备能力缓存或明确报告数据缺口。
3. 后端验证设备身份、设备与宠物的绑定关系、数据结构、时间戳和数据范围。
4. 通过校验的数据进入存储层，并保留必要的数据来源、采集时间、接收时间和质量状态。
5. 业务服务向有权限的用户提供位置、活动趋势、设备状态和事件信息。
6. AI 服务（未来接入时）仅消费经过授权和质量检查的数据，并输出带有模型版本、时间范围和置信信息的辅助结果。

规划中的控制下行链路：

1. 已授权主人在应用中明确发起设备控制操作。
2. 后端校验用户、宠物、设备绑定关系、操作权限、设备在线状态和安全限制。
3. 生成可追踪的控制指令，发送至设备并等待设备确认。
4. 设备执行前再次检查本地安全条件；执行后回报状态。
5. 后端记录请求者、目标设备、指令、时间、确认结果和停止原因。
6. 对于停止指令，应设置高于普通启动/调整指令的处理优先级，并设计通信中断时的本地安全策略。

上述链路是目标设计。实际传输协议、消息队列、数据库和服务拆分必须在技术选型与验证后确定。

### 5.2 设备身份与宠物绑定

设备上报不能仅凭客户端传入的宠物 ID 就认定数据归属。后端应验证：
- 设备身份凭据是否有效、是否已撤销
- 设备是否处于允许上报的状态
- 设备与宠物的绑定关系在采集/接收时是否有效
- 设备是否被重复绑定或发生转移
- 数据是否重复、过期、格式错误或时间异常

绑定、解绑和设备转移应有权限检查和审计记录。设备密钥、配对码和令牌不得写入公开仓库或普通日志。

### 5.3 数据模型建议（待结合实际数据库落地）

以下是逻辑实体建议，不代表当前数据库中已经存在同名表或字段：

| 逻辑实体 | 主要职责 | 需要关注的字段/关系 |
|---|---|---|
| Pet | 宠物档案 | 宠物标识、主人/归属关系 |
| Device | 项圈设备 | 设备标识、设备类型、固件版本、状态 |
| DeviceBinding | 设备与宠物绑定历史 | 设备、宠物、生效/失效时间、操作者 |
| SensorRecord | 传感器记录 | 设备、宠物、传感器类型、数值/单位、采集时间、接收时间、质量状态 |
| LocationRecord | 定位记录 | 坐标、定位时间、精度/来源、可信度状态 |
| Geofence | 电子围栏配置 | 宠物、区域定义、启用状态、创建者 |
| GeofenceEvent | 围栏事件 | 事件类型、触发位置、时间、判断依据、通知状态 |
| FamilyMembership / Permission | 家庭成员与授权 | 用户、家庭/宠物范围、角色、权限、授权状态 |
| LostPetEvent / Sighting | 走失事件与线索 | 事件、最后可信位置、线索内容、提交者、授权和核验状态 |
| DeviceCommand | 设备控制指令 | 目标设备、请求者、指令类型、参数、安全检查、确认和结果 |
| DeviceAuditLog | 设备操作审计 | 操作者、操作、目标、时间、结果和必要上下文 |

设计原则：
- 重要记录应有稳定 ID 和明确的时间语义；区分设备采集时间与服务器接收时间。
- 坐标、温度和活动数据必须记录单位、来源和质量信息，不能只保存一个无上下文的数值。
- 位置与家庭成员数据属于敏感信息，应实施最小权限、访问审计和合理的数据保留策略。
- 数据库字段、索引、外键、迁移策略和实际实体关系，必须以最终实现为准并在本手册中更新。

### 5.4 定位质量与“最后可信位置”

定位页面和业务服务应区分实时/最新上报位置与最后可信位置。可信度判断可考虑：
- 定位数据的采集时间和服务器接收时间
- 定位精度或设备提供的质量指标
- 设备在线状态和连续数据情况
- 明显不合理的跳点或速度变化
- 定位来源和硬件能力

不应把离线前的旧坐标标记为实时位置。可信度规则需要通过真实设备数据评估，阈值不可凭空设定。

### 5.5 电子围栏规则

电子围栏是确定性业务规则，不是机器学习模型。实现时应明确：
- 围栏归属的宠物和管理者
- 区域形状、坐标系和边界规则
- 是否启用、规则生效时间
- 定位数据新鲜度和质量要求
- 进入/离开判定、连续确认或抖动抑制策略
- 误报处理、通知去重和事件审计

定位质量不足、数据过期或设备离线时，应将状态表达为“无法确认”或类似状态，而不是直接推断宠物越界。具体规则需经过实测。

### 5.6 多宠物与家庭共享权限

所有宠物、设备、位置、轨迹、围栏、走失事件和设备控制接口都必须进行后端资源级授权。建议采用最小权限原则：
- 宠物主人/管理员：管理宠物资料、设备绑定、家庭成员和关键设置。
- 家庭成员：仅访问明确授权的宠物与功能。
- 受限成员：只拥有指定的查看或有限操作权限。

必须验证：跨用户访问、猜测 ID 访问、撤销授权后的访问、设备解绑后的访问，以及 Socket.IO 房间/事件订阅权限。前端路由守卫或隐藏按钮不能替代后端授权。

### 5.7 社区协同寻宠流程

规划流程可包括：
1. 宠物主人创建走失事件，并确认要公开的信息和位置范围。
2. 系统展示经过授权的最后可信位置及其时间，不泄露不必要的家庭隐私。
3. 协助者在授权范围内提交目击线索。
4. 系统进行格式校验、去重和可选的辅助匹配。
5. 由主人或授权人员进行人工核验、联系和状态更新。
6. 事件结束后按隐私和数据保留规则处理信息。

AI 匹配只能提供辅助线索，不应自动认定宠物身份或自动公开私人位置。

### 5.8 舒适护理控制与安全机制

舒适护理（例如震动/触觉输出）属于高风险设备控制路径，必须在硬件和软件两侧设置保护。正式开放前至少完成电气、温升、机械接触、强度、最长运行时间、误触发和异常断连等评估。

控制链路应遵循：
- 仅允许有明确权限的主人主动确认启动。
- 后端校验授权、设备绑定、设备状态和安全参数。
- 设备本地再次校验允许的强度与时长边界。
- 采用经过验证的强度档位和最长运行时间；参数不得由不可信客户端任意指定。
- 启动后必须能查询状态，并对指令确认/超时进行明确处理。
- AI 结果不得直接生成或触发护理启动命令。

至少设计三种停止机制：
- **到时停止：** 达到安全配置允许的时长后，由设备本地计时器或可靠控制逻辑自动关闭输出；不能只依赖网络定时消息。
- **主人停止：** 主人可主动停止；停止指令应具有优先级，并在设备端尽快关闭输出。界面应显示停止请求和设备确认状态，不能把“已发送”误报为“已停止”。
- **异常停止：** 设备发现预先定义的异常、运行条件不满足或无法确认安全状态时，进入安全停止状态，并在通信可用时上报异常。具体可检测项目取决于实际传感器和硬件设计。

网络中断、服务器不可用或控制状态不明时，设备必须有本地超时和安全停止策略。停止路径应优先于启动/调整路径，并记录停止原因。未完成安全验证前，不得开放真实宠物使用。

### 7.1 智能项圈接口边界（规划，非现有接口清单）

### 7.2 实时通信安全

如采用 Socket.IO 或其他实时通信机制，应：
- 在连接建立时验证用户身份，并在订阅资源时校验其宠物/设备访问权限。
- 对每个房间、频道和事件执行资源级授权，防止通过猜测房间名访问他人数据。
- 对设备上报与用户控制指令区分消息方向、身份和权限。
- 对控制指令实施防重放、超时、确认和审计设计。
- 在令牌过期、用户退出、权限撤销或设备解绑时，及时终止相关订阅。
- 不在日志或错误响应中泄露令牌、设备密钥、精确位置等敏感内容。

## 9. 前后端开发规范

待结合项目实际工具配置确定代码风格、命名、组件边界、错误处理、日志规范和 Git 提交约定。

智能项圈相关实现建议保持职责分离：
- 设备固件负责传感器采集、本地安全检查、执行器控制和断网保护。
- 后端负责设备身份、数据接入、资源授权、业务规则、指令管理和审计。
- 前端负责展示状态、收集用户明确授权和展示操作结果，不自行决定用户是否有权限。
- AI 服务负责经授权数据的辅助分析，不直接越过业务权限和设备安全控制层。

- 定位漂移、过期位置、可信度不足和围栏边界抖动测试
- 多宠物隔离、家庭成员权限、权限撤销和越权访问测试
- 走失事件隐私范围、线索提交、人工核验和审计测试
- 设备离线、低电量、控制指令超时、重复指令和状态不一致测试
- 护理到时停止、主人停止、异常停止、断网本地停止和启动/停止竞争测试
- 硬件电气安全、温升、强度和长时间运行评估

没有执行记录的测试不得标记为通过。未完成硬件安全验证的舒适护理功能不得用于真实宠物。

## 11. 部署与运维

待确认正式服务提供商和部署方式后补充：
- 前端部署
- 后端部署
- 数据库与文件存储
- 域名、HTTPS 与跨域配置
- 环境变量管理
- 日志、监控、告警
- 回滚与故障排查

如后续部署设备接入服务或消息基础设施，还需明确设备认证材料轮换、证书更新、连接限流、离线缓存、积压监控、数据重放和故障恢复策略。

## 12. AI 能力开发规范（规划）

PetHome V2.0 计划探索 RAG 知识助手、机器学习推荐、健康辅助和计算机视觉能力。相关实现尚需独立设计、数据合规审查、基线实验和验收。

智能项圈数据可能成为未来模型输入，但必须先完成数据质量、采集授权、标注规范和代表性评估。可探索的方向包括活动/行为识别、个体趋势分析、异常变化提示和走失线索辅助匹配。

每项 AI 功能至少记录：
- 业务问题与适用范围
- 数据来源、授权与脱敏方式
- 模型/算法名称、版本和配置
- 数据集划分、基线和评价指标
- 错误案例、偏差与已知限制
- API、安全边界、成本和延迟
- 人工复核与回退机制

规则匹配不得描述为训练所得的机器学习模型；调用大语言模型也不自动等于完成 RAG。AI 不得绕过用户权限、电子围栏规则或设备控制安全检查，也不得自动触发舒适护理。

## 13. 安全规范

重点核查认证授权、敏感信息日志、密钥管理、CORS、文件上传、Socket.IO 事件权限、依赖漏洞和个人信息保护。

智能项圈接入还应重点考虑：
- 每台设备独立身份凭据，支持撤销和轮换。
- 设备与宠物绑定关系必须由服务端验证。
- 传输链路应采用适当的加密和完整性保护。
- 位置、轨迹、家庭成员关系和设备控制操作按敏感信息保护。
- 控制命令应校验授权、参数边界、时效和重复提交。
- 设备本地具备独立于云端的安全停止能力。
- 对设备异常和高风险控制操作保留必要审计记录。

## 14. 故障排查

待根据真实开发与部署问题持续补充，保留可复现步骤、错误信息（脱敏）、根因、修复和验证证据。

智能项圈联调时应分别判断设备采集、设备网络、服务端接入、数据存储、权限校验和前端展示环节，避免仅凭页面无数据就推断传感器损坏。日志和诊断信息必须脱敏。

## 15. 贡献与发布流程

待确定分支策略、Pull Request 检查项、代码审查、版本号、变更记录和发布验收流程。

涉及设备控制、定位隐私、家庭共享权限或 AI 决策边界的变更，应要求专项审查和对应测试证据；安全停止策略不得在未评估影响的情况下被移除或弱化。
